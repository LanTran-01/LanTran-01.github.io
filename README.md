# www.lantran.dev

The site is organised as **Tech** (interactive technical projects) and **Tarot**,
all served by GitHub Pages from the root of `main`:

| URL | What | Source |
|---|---|---|
| [lantran.dev](https://www.lantran.dev/) | Home page: one full-screen section per project, Tesla-style; a **Tech** menu groups the technical projects | `home/` (plain HTML/CSS) |
| **Tech · 01** [lantran.dev/tech/gundam/](https://www.lantran.dev/tech/gundam/) | Ξ Hardware Explorer, an engineering-style 3D explorer of the RX-105 Ξ Gundam | `explorer/` with `MACHINE=gundam` |
| **Tech · 02** [lantran.dev/tech/cubesat/](https://www.lantran.dev/tech/cubesat/) | CubeSat Systems Explorer, an illustrative 3U satellite and its embedded electronics | `explorer/` with `MACHINE=cubesat` |
| [lantran.dev/tarot/](https://www.lantran.dev/tarot/) | ARCANA, a minimalist tarot reading app | `arcana/` (React), see [arcana/README.md](arcana/README.md) |

Both Tech projects are built from **one explorer engine** (`explorer/`) with a
machine module per subject; see [Machines](#machines-one-engine-several-subjects).

## Repository layout

```
/                    the built site (generated by scripts/publish-site.mjs; do not edit by hand)
  index.html         ← copied from home/
  assets/            ← copied from home/ (styles, font, product shots)
  tech/gundam/       ← explorer/dist/gundam   (base /tech/gundam/)
  tech/cubesat/      ← explorer/dist/cubesat  (base /tech/cubesat/)
  tarot/             ← arcana/dist
  gundam/index.html  ← generated: forwards the old /gundam/ home to /tech/gundam/
  404.html           ← generated: routes deep links back into the right app
  CNAME              custom domain (never touched by the publish script)
home/                source of the home page
explorer/            source of the shared explorer engine and its machines (Ξ Gundam, CubeSat)
arcana/              source of ARCANA
scripts/             publish-site.mjs
```

## Publishing

GitHub Pages serves the repository root of `main` with no CI step, so the built
site is committed:

```bash
node scripts/publish-site.mjs   # builds both explorer machines and arcana, then assembles the site at the root
git add -A && git commit -m "Publish site" && git push
```

`npm run publish:site` in either app runs the same script. Add `--skip-build`
to republish the existing `dist/` folders, for example after editing only `home/`.
The script only removes paths it wrote last time (tracked in `.site-manifest.json`)
and never touches `CNAME`, `README.md` or the source folders.

Deep links such as `/tech/cubesat/explore/imu` work through `404.html`, which redirects
to `/tech/cubesat/?redirect=…`; a small inline script in the explorer's `index.html` restores
the real URL before the router starts. Older explorer URLs keep working: `/gundam/` is a
redirect page, and `/gundam/explore/head`, `/explore/head` and `/systems?node=…` are
forwarded to their `/tech/gundam/` equivalents. `/tech` opens the Tech section of the home page.

The home page's product shots are rendered from each app's dev harness:
`explorer/harness/model.html?view=three-quarter&zoom=…` (per machine) and `arcana/harness/showcase.html`.

# Ξ Hardware Explorer (`/tech/gundam/`)

An interactive, engineering-style 3D explorer for the RX-105 Ξ (Xi) Gundam from
*Mobile Suit Gundam: Hathaway*. Select an assembly, cut away its armor, explode
its subassemblies, and trace a conceptual systems architecture that stays linked
to the 3D model.

> **Read this first — what is and isn't real.**
> The 3D machine is a **procedural prototype**, a silhouette study built from
> three.js primitives. It is not an accurate or licensed model of the Xi Gundam.
> All internal hardware, subassembly breakdowns and the systems map are
> **conceptual visualizations** invented for this project, not canon. In the data,
> rows marked `reference` repeat only broad, non-numeric descriptors that are widely
> published (for example, that the RX-105 carries a Minovsky flight system).
> Everything else is marked `conceptual`. No engineering measurements, power
> ratings or materials are claimed.
>
> RX-105 Ξ Gundam and Mobile Suit Gundam Hathaway are trademarks of their owners
> (Sotsu · Sunrise / Bandai Namco Filmworks). This is an unofficial fan engineering study.

## Running the explorer locally

Requires Node 20+ (installed here with `brew install node`).

```bash
cd explorer
npm install
npm run dev            # Ξ Gundam  · http://localhost:5173/tech/gundam/
npm run dev:cubesat    # CubeSat   · http://localhost:5174/tech/cubesat/
npm run typecheck      # tsc, strict — checks the engine against both machines
npm run lint           # eslint
npm run build          # production builds into explorer/dist/gundam and explorer/dist/cubesat
```

## Using the explorer

| Action | Input |
|---|---|
| Rotate / zoom / pan | drag · wheel or pinch · right-drag or two-finger drag |
| Select an assembly | click it on the model or in the index |
| Inspection modes | Exterior · Cutaway · Exploded (with distance slider) · Architecture (3D callouts), or keys `1`–`4` |
| Subassemblies | click in the hardware tree, a callout, or on the model in an inspection mode |
| Previous / next assembly | `←` / `→` |
| Back / reset | `Esc` (clears the subassembly first, then returns to the full machine) · `R` resets the camera |
| Systems map | `/tech/gundam/systems`: click a node to highlight its linked assemblies in 3D; click the model to filter nodes |

Routes (under `/tech/gundam`): `/` overview · `/explore/:slug` (head, cockpit, shoulders, arms, waist,
legs, feet, backpack, thrusters, weapons) · `/systems?node=<id>`.

## Architecture

The 3D canvas is mounted once in `AppShell` and never remounts. Routes only
render overlays, so moving between assemblies and the systems map keeps the
scene, the camera and the loaded model.

```
explorer/
  machines.config.ts           build targets: base path, page title and description per machine
  src/
    machines/gundam/           everything specific to the RX-105 (see "Machines" below)
    machines/cubesat/          everything specific to the CubeSat
    data/                      shared types and lookups over the active machine (@machine)
      types.ts                 domain types + MachineConfig contract
      components.ts, subsystems.ts, modelConfig.ts, machine.ts
    state/explorerStore.ts     zustand store (URL owns selection; store owns mode, hover, explode…)
    features/model/
      modelTypes.ts            mesh tagging contract (userData.xi = PartTag)
      procedural/primitives.ts shared geometry kit (Kit<Palette>, extrude, merge, bilateral…)
      loadModel.ts, annotateModel.ts, useMachineModel.ts   procedural or GLB → indexed model
      materialController.ts    per-mesh material state
    features/component-inspection/modeVisuals.ts   mode tuning (assembly scope and machine scope)
    features/hardware-architecture/                diagram layout, edge routing, pan/zoom
    components/viewer/         R3F scene, camera rig, interaction, hover label, 3D callouts
    components/inspection/     inspection panel sections (identification, modes, tree, data)
    components/architecture/   systems diagram, node detail, legend, controls
    components/layout|navigation/ top bar, status bar, sheets, index, dialogs, view-mode bar
    pages/                     ExplorerPage, ComponentDetailPage, SystemsPage
```

### Machines: one engine, several subjects

The engine never imports a machine directly. `@machine` is a build-time alias
(`MACHINE=<id>`, default `gundam`) to `src/machines/<id>/`, and only the
`src/data/*` modules and the model hook read it. Each machine provides:

| File | Contents |
|---|---|
| `ids.ts` | `ComponentId`, `SystemLane` and `FlowKind` unions |
| `catalogue.ts` | `COMPONENTS`: names, descriptions, function/role, interfaces, flows, subassembly tree, tech data, expandable notes, camera hints |
| `systems.ts` | systems map: lanes (with tones), flow kinds (with stroke and dash), columns, nodes, edges |
| `model.ts` | `modelConfig` (GLB path, mesh rules) and the procedural `build`/`dispose` |
| `procedural/` | geometry and material palette, built with the shared `Kit` |
| `machine.tsx` | presentation: wordmark, identification panel, terms ("assembly" / "component"), inspection modes and their scope, layer and basis labels, About dialog, stage and overview camera |

`modes.scope` is the one behavioural switch. Ξ Gundam uses `"assembly"`: modes
isolate the selected assembly and reset when the selection changes. CubeSat uses
`"machine"`: Exterior / Internal / Exploded apply to the whole satellite, persist
across selections, and the exterior view switches to the internal one when the
part you select or link from the systems map has nothing visible from outside.

`npm run typecheck` checks the engine once per machine (`tsconfig.gundam.json`,
`tsconfig.cubesat.json`). To add a machine, copy one of the folders, register it in
`machines.config.ts`, add a tsconfig and a build step, and give it a target in
`scripts/publish-site.mjs`.

### Replacing the prototype with a real model

1. Put a GLB/GLTF you have the rights to use in `explorer/public/gundam/models/`
   (for example `xi-gundam.glb`).
2. Open the site with `?model=gltf`, set `source: "gltf"` in
   `src/machines/gundam/model.ts`, or build with `VITE_MODEL_URL=/tech/gundam/models/file.glb`.
3. Edit `meshRules` in `model.ts` so mesh and node names map onto the
   10 assemblies. Meshes are scaled to the target height and placed on the floor.

If the GLB fails to load, the viewer falls back to the procedural prototype and
says so in the status bar. A GLB usually has no internal geometry or explode
vectors, so Cutaway and Exploded are disabled with an explanation for any
assembly that lacks them. The capabilities come from the geometry actually present.

### Dev tools

- `explorer/harness/model.html` (served at `/tech/<machine>/harness/model.html` in dev) is a standalone model inspector with these
  options: `?view=front|side|back|three-quarter`, `?explode=0..1`,
  `?layer=internal`, `?focus=<assembly>`, `?probe=1`.
- `npm run shot -- <url> <out.png> [--w --h --mobile --click --drag --eval …]`
  takes a headless screenshot and reports any console errors. It needs
  `npx playwright install chromium` once.

## Known limitations

- The prototype's proportions are approximate. The pure side view is its weakest
  angle, because the pauldrons hide the head.
- Some data subassemblies (for example `cp-env`) have no geometry. The tree marks
  them "not modelled".
- The thruster array spans the whole body, so its close-up is necessarily wide.
- On narrow phones, the architecture-mode callouts are truncated.
- three.js is pinned to r182. React Three Fiber 9.8 still uses `THREE.Clock`,
  which r183+ deprecates with a console warning.

# CubeSat Systems Explorer (`/tech/cubesat/`)

An interactive explorer for an illustrative 3U CubeSat, focused on embedded
systems and system integration: open the structure, separate the electronics
stack, inspect each subsystem and trace how power, data, commands and radio links
connect them. It runs on the same engine as the Ξ explorer.

> **What is and isn't real.** The satellite is a **generic educational design**
> built from primitives, not a specific spacecraft. Rows marked `reference` state
> general, widely documented facts (for example that CubeSat sizes are counted in
> standard units, or that a GNSS receiver is optional). Everything marked
> `conceptual` is the example architecture chosen for this model. No dimensions,
> electrical ratings, radio frequencies, protocols or control algorithms are
> specified, and real CubeSats choose among these subsystems.

## Using it

| Action | Input |
|---|---|
| Rotate / zoom / pan | drag · wheel or pinch · right-drag or two-finger drag |
| Select a component | click it on the model or in the index |
| Views (whole satellite) | Exterior · Internal · Exploded, keys `1`–`3`; the bar at the top right on the overview and systems map, section B in the inspection panel |
| Explode distance | slider beside the view bar, or in the inspection panel |
| Subassemblies | click in the hardware tree, or on the selected component in the Internal/Exploded view |
| Back / reset | `Esc` clears the subassembly, then returns to the full satellite, then to the assembled Exterior view · `R` resets the camera |
| Systems map | `/tech/cubesat/systems`: select a node to highlight its components in 3D; click the model to filter nodes |

Components (`/tech/cubesat/explore/:slug`): `onboard-computer`, `gnss`, `imu`,
`power`, `battery`, `solar`, `comms`, `antenna`, `payload`, `adcs`, `structure`.
Each has a short description, its function and role, interfaces, relationships,
technical rows tagged by basis, and collapsible engineering notes.

The model (`src/machines/cubesat/procedural/`, about 210 meshes) stacks the
boards along the long axis: payload optics and electronics in the nadir unit;
ADCS board, reaction wheels, magnetorquers, battery and power management in the
middle unit; onboard computer, IMU, GNSS receiver and radio in the zenith unit;
the antenna deployer and GNSS patch on top. Explode offsets live in
`procedural/layout.ts`.

## Known limitations

- The model is illustrative; proportions follow the 3U form factor but nothing is to scale.
- Inside a closed stack, boards are best seen in the Internal view (other internals
  turn to glass while one is selected) or the Exploded view.
- On narrow phones the satellite is framed by its wingspan, so it starts small; pinch to zoom.
- There is no 3D callout ("Architecture") mode for the CubeSat; its modes are the
  three whole-satellite views.
